## Problem Statement

When a Portugal roundup article drops (TimeOut, Observador, a food blog), turning it into a NomNom list plus Instagram video and stills is hand work: read the article, search each restaurant, build the list, then run ListShowcase. Names do not match (accents, old names, "the one in Chiado"), so spots get skipped or duplicated.

## Demand Evidence

Operator demand, not waitlist demand. The content operator already pays this tax every time list content is needed. Status quo is the evidence: the workflow exists and is slow. No user-facing "paste a URL" product in this wedge.

## Status Quo

Read the article → search each restaurant in NomNom → create the list by hand → run content-machine / `fetch-list-props.mjs` / ListShowcase. Matching is the failure mode.

## Target User & Narrowest Wedge

User: NomNom content operator.
Wedge this week: internal CLI. Paste article URL → extract restaurants with evidence quotes → match existing NomNom rows → confirm JSON → create list → render ListShowcase video + one still per restaurant showing community rating and location.

## Constraints

- Data honesty (content-machine): never invent a restaurant, rating, quote, or location.
- Never auto-post.
- Portuguese name matching must stay accent-insensitive.
- Unmatched names stay unmatched until a human ingest. Same rule as Google Maps list import.

## Premises

1. Internal ops script this week, not a user-facing paste-URL feature.
2. Never invent a restaurant. Unmatched names stay unmatched until ingest.
3. Reuse ListShowcase for the video. Add per-spot stills from NomNom data, not a new composition.
4. Slides show NomNom `restaurants.rating` and `home_city.name` (municipality). Never the magazine's score. Neighbourhood (Chiado) is article context for the human, not a field ListShowcase currently paints.

## Approaches Considered

- **A — Confirm JSON then render** (chosen): article URL → extract `{name, area, evidence}` → candidate search + name score → review JSON → service-role list insert via `buildListItemRows` → ListShowcase + per-spot stills.
- **B — Content-machine lane now**: same pipeline plus ledger and `--type article-list`. Ruled out for this week; more files than the wedge needs.
- **C — Auto-ingest unmatched from Google**: ruled out because matching is the stated pain; auto-create is how you get the wrong Chiado row.

## Recommended Approach

**A.** Same honesty as Google Maps list import: extract places from a URL, match existing NomNom rows, never insert restaurants. Articles need a new extractor and a new candidate search. They do not reuse `matchOnePlace` (needs lat/lng) and they do not reuse `create_user_list` (needs `auth.uid()`). They reuse `normalizeName` / `nameMatchScore`, `buildListItemRows`, and service-role writes.

### CLI

```bash
# 1) extract + match → review.json (no DB writes)
node remotion/scripts/article-to-list.mjs --url <article> --name "Lisbon weekend tables"

# 2) after you edit decisions, create list + render
node remotion/scripts/article-to-list.mjs --confirm remotion/content-queue/article-lists/<slug>/review.json --render
```

`--user-id` and `OPERATOR_USER_ID` are both required on `--confirm` and **must be equal**. Remotion `getSupabase()` is service-role with **no** `auth.uid()`. Do **not** call `create_user_list` (it raises `not_authenticated` without a user JWT). Insert `lists` with `user_id = --user-id` (must exist in `public.users`), `visibility = private`, `published_at` null. Do **not** put the article URL in `lists.description` (`fetch-list-props` paints description on the intro). Keep `source_url` in `review.json` and the CLI log. After insert, mint `slug` with Remotion `getSupabase()` using the `ensureListSlug` algorithm — do not import `ensure-list-slug.js` (it pulls Next `supabaseAdminClient`). Then insert `list_items` via `buildListItemRows` (`added_by = --user-id`, article order, deduped).

Output dir is always `remotion/content-queue/article-lists/<slug>/` with `review.json`, then `list.mp4`, `poster.jpg`, `spot-01.jpg` …

### Fetch

`fetch` HTML. If `<body>` text after stripping scripts/styles is under 500 characters, fail closed (no Playwright in v1). First fixture should be a static-enough article; add a host parser or Playwright only after that fixture fails.

### Extract

Do not import `src/libs/restaurant-ingest/qwen-json-chat.js` from Remotion (Next/Sentry). Copy the HTTP JSON-chat loop into `remotion/scripts/lib/qwen-json-chat.mjs`.

Prompt returns `{ restaurants: [{ name, area, evidence }] }` (json_object, not a bare array). `maxTokens` ≥ 4096. Portuguese + English names allowed. Only named restaurants, no magazine scores.

Drop a row if `evidence` is missing or `articleText` does not contain it (whitespace-normalized). Also drop unless `normalizeName(name)` appears in `normalizeName(articleText)` — evidence-only would let Qwen invent a venue next to a real sentence. If `articleText.length > 12000`, split into 8k windows with **1k overlap**, extract per chunk, then merge. Merge key is `normalizeName`. Same key: keep the first-seen row (article order); if later chunks add a different `evidence` string, append with ` | `; if `area` is empty on the first row, take the first non-empty later area. After merge, cap at the **first 20** first-seen names.

Copied Qwen helper **fails closed** (no empty `review.json` that looks successful). Require `QWEN_API_KEY`, `QWEN_BASE_URL`, and `QWEN_MODEL` after the same dotenv load as `remotion/scripts/lib/supabase-client.mjs`. Defaults if you need them for a local note: intl DashScope URL and `qwen-turbo` — but missing env is a crash, not a silent default.

### Match (this is new code, wrapping the existing scorer)

`pickRestaurantMatch` only scores a candidate list. It does not search, and it has no `ambiguous` status (ties without coords pick the first row).

Candidate recall (v1, no new DB extension): two PostgREST `.ilike('name', '%q%')` queries — raw extract name and JS-stripped (`normalizeName`) name — merge ids, limit 25, then score in JS. `Promise.all` the two queries per name; run at most **5 names** at a time. Residual: `Pérola` vs `Perola` may miss until a later `unaccent` RPC (TODOS.md). Do not write SQL `unaccent()` through PostgREST.

Export `nameMatchScore` from `pick-restaurant-match.js`. Put `matchRestaurantByName({ name, candidates })` next to it in `src/libs/lists` (not remotion).

`area` from the article is usually a neighbourhood (Chiado), not `cities.name` (Lisboa). Do not filter candidates to `home_city = area`. Old names and “the one in Chiado” are **not** auto-solved. The review file is the disambiguator: human picks among a shortlist.

Statuses (do not call `pickRestaurantMatch` as if it returned three states):

| status | when | auto-decision |
|---|---|---|
| `matched` | exactly one candidate with name score **3** (exact `normalizeName`) | pre-fill `decision: accept` |
| `ambiguous` | zero exact matches but ≥1 candidate with score **2**, or ≥2 score-3 | `decision: null`; include `candidates[{id,name,address,city}]` |
| `not_found` | no candidate with score ≥2 | `decision: drop`. Re-run after ingest; do not paste arbitrary ids. |

Never auto-accept containment (score 2). Never geo-only match.

### Review JSON schema

```json
{
  "source_url": "https://…",
  "list_name": "Lisbon weekend tables",
  "list_id": null,
  "confirmed_at": null,
  "extracted": [
    {
      "name": "Cervejaria Ramiro",
      "area": "Intendente",
      "evidence": "Ramiro still queues out the door",
      "status": "matched",
      "restaurant_id": "uuid-or-null",
      "candidates": [],
      "decision": "accept",
      "picked_id": null
    }
  ]
}
```

`decision` is `accept` | `drop` | `pick`. Confirm resolver: `pick` uses `picked_id` (must be in `candidates`); `accept` uses `restaurant_id` (uuid, from auto-match); `drop` uses neither. Refuse if ids are missing or mixed. `--confirm` also refuses unless every row has a decision, `list_name` is non-empty, and the operator sets `confirmed_at` (ISO) or passes `--i-confirmed`.

Re-confirm: if `list_id` is set, verify `lists.user_id === --user-id`, **delete** existing `list_items` for that list, then `buildListItemRows` + insert. Maps upsert does not delete dropped rows. Write `list_id` back into `review.json`. If `list_id` is null, insert a new list.

Two extract rows may resolve to one restaurant: keep both rows in JSON; `buildListItemRows` dedupes ids. `--name` is required on first run (do not guess from `<title>` until a fixture proves it).

Confirm resolver is a **pure function** in `src/libs/lists/article-list-confirm.js`. The Remotion CLI is a thin wrapper. Tests live under `src/**/__tests__` (root `npm test` does not run `remotion/scripts/__tests__`).

### Render

Abort `--confirm` if accepted unique restaurants < `MIN_LIST_PLACES` (3). Video: pass `--places min(8, accepted)` so a 20-place roundup is not a ~68s reel (`scoreList` already warns above 33s). Stills: one frame per **accepted** restaurant, not truncated to 8.

`fetch-list-props.mjs` must `.order('sort_order')` (tie-break `created_at`). Today it orders by `created_at` only (`:71-75`), so a batch insert loses article order.

`npx remotion render ListShowcase` then stills:

- poster: existing intro frame (today `stillFrame` 60)
- per spot: `frame = spots[i].start + floor(spots[i].duration / 2)` from `buildListTimeline`; files `spot-01.jpg` …

Ken Burns at ~1.45s is acceptable. Captions and content-machine ledger are out of this wedge (later `--type article-list`).

`Scene2Spot` already shows `home_city.name` (municipality, not neighbourhood) and ★ `restaurants.rating`. Hide the star if rating is null. Per-spot city line shows whenever `home_city` exists. List intro subtitle hides mixed cities (existing `fetch-list-props` behaviour). Do not show the article's ranking.

Unmatched names print at the end. Do not call restaurant ingest from this script.

## Success Criteria

- One real Portugal roundup article → confirmed list of only matched NomNom restaurants.
- Zero restaurants on the list that were not in the DB before the run.
- Video + N stills (one per list place) each showing ★ rating when present and municipality (`home_city`) when present.
- Unmatched names reported, none silently dropped without a line in the review JSON.
- Time from URL to review JSON under a few minutes; confirm + render is the existing Remotion wait.
- Auto-accepted rows are exact `normalizeName` matches only. Old names / “the one in Chiado” are never auto-accepted. They are `ambiguous` only if SQL recall found candidates; otherwise `not_found` (ingest, then re-run).
- Video may show at most 8 places; stills cover every accepted restaurant.

## Data flow

```
URL --fetch--> articleText (<500 chars: FAIL CLOSED)
         |
         v
    Qwen json_object {restaurants:[{name,area,evidence}]}
         |  fail closed if env/JSON missing
         v
    drop if evidence not in text
    drop if normalizeName(name) not in article
    chunk/merge/cap 20
         |
         v
    per name (max 5 concurrent):
      ilike raw  ||  ilike normalizeName  --> merge 25 --> nameMatchScore
         |
         +-- score 3 unique --> matched / accept
         +-- score 2 or 2x score-3 --> ambiguous / decision null
         +-- else --> not_found / drop
         v
    review.json  --human edit-->  --confirm
         |                         |
         |                    uid == OPERATOR_USER_ID
         |                    insert lists + slug
         |                    DELETE list_items if re-confirm
         |                    buildListItemRows
         v
    fetch-list-props --places min(8,n)  --> ListShowcase.mp4 + poster
    stills: all accepted, frame = spot.start + floor(dur/2)
```
